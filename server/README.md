# TypeScript Compiler Server

A high-performance HTTP server that provides TypeScript type checking and JavaScript compilation using the TypeScript-Go compiler and esbuild.

## Features

- **TypeScript type checking**: Full TypeScript type checking with detailed diagnostics
- **JavaScript bundling**: Uses esbuild for fast, optimized JavaScript output
- **Self-contained projects (v3)**: Caller provides all deps, config, and source files — server assumes nothing
- **Automatic dependency caching**: 3-tier cache (local disk, S3, bun install) keyed by lockfile hash
- **S3-backed module system (v1/v2)**: Node modules and type definitions loaded from S3
- **High performance**: ~155ms average build time, ~208ms typecheck (including network latency)

### V3 API (Recommended)

V3 is the self-contained API. The caller provides everything: source files, dependencies (`package.json` + `bun.lock`), TypeScript config (`tsconfig.json`), and esbuild options. The server has no hardcoded compiler options, no hardcoded packages, and no version concept.

#### `POST /v3/typecheck`

Typechecks all TypeScript files in the upload using the caller's `tsconfig.json` (or sensible defaults).

#### `POST /v3/compile`

Compiles and bundles the project using esbuild. Entry point is read from `package.json#main`. Typechecks first by default.

**Query Parameters:**
- `skip_typecheck=true` — skip the typecheck step, compile only

#### Request Format

`Content-Type: multipart/form-data`

Each multipart part's **field name is the file path** (absolute, rooted at `/`). The server reads all parts into a map of path to content.

```
POST /v3/typecheck HTTP/1.1
Content-Type: multipart/form-data; boundary=----abc

------abc
Content-Disposition: form-data; name="/package.json"

{"main": "./src/index.ts", "dependencies": {"zod": "^3.23.0"}}
------abc
Content-Disposition: form-data; name="/bun.lock"

<lockfile contents>
------abc
Content-Disposition: form-data; name="/tsconfig.json"

{"compilerOptions": {"strict": true, "jsx": "react-jsx", "jsxImportSource": "@crayonnow/core"}}
------abc
Content-Disposition: form-data; name="/src/index.ts"

import { z } from 'zod';
export const schema = z.object({ name: z.string() });
------abc--
```

#### Required Files

| File | Purpose |
|------|---------|
| `/package.json` | Declares dependencies, entry point (`main`), and optional esbuild config |
| `/bun.lock` | Lockfile pinning exact dependency versions (generated by `bun install` at dev time) |

#### Optional Files

| File | Purpose |
|------|---------|
| `/tsconfig.json` | TypeScript compiler options. If absent, defaults are used (see below) |

All other files are treated as source files. Paths must not start with `/node_modules/` (reserved for installed deps).

#### Limits

- Max 100 source files per request (plus `package.json`, `bun.lock`, `tsconfig.json`)
- Max 1 MB per file
- Max 10 MB total payload

#### Response Format

```json
// typecheck success
{"pass": true}

// typecheck errors
{
  "errors": [
    {"file": "/src/index.ts", "message": "Type 'number' is not assignable to type 'string'.", "line": 1, "column": 5}
  ]
}

// compile success
{"code": "...bundled JavaScript..."}

// compile errors
{
  "errors": [
    {"file": "/src/index.ts", "message": "...", "line": 1, "column": 5}
  ]
}
```

#### Error Responses

| Status | Meaning |
|--------|---------|
| 400 | Bad request — missing required files, invalid JSON, file too large, etc. |
| 405 | Method not allowed — must use POST |
| 502 | Dependency installation failed — `bun install` error (stderr included in response) |

### package.json

The `package.json` uploaded to v3 serves four purposes:

1. **Entry point**: The `main` field tells the compile endpoint where to start bundling.
2. **Dependencies**: `dependencies` and `devDependencies` are installed by bun when not cached.
3. **Private packages**: The optional `resolve-s3` field lists packages to fetch from S3 instead of npm.
4. **esbuild config**: The optional `esbuild` field configures the bundler.

#### Minimal example

```json
{
  "main": "./src/index.ts",
  "dependencies": {
    "zod": "^3.23.0"
  }
}
```

#### With private packages and esbuild config

```json
{
  "main": "./src/index.ts",
  "dependencies": {
    "@flickfyi/core": "0.0.8",
    "@flickfyi/photon": "0.0.3",
    "zod": "^3.23.0"
  },
  "resolve-s3": ["@flickfyi/core", "@flickfyi/photon"],
  "esbuild": {
    "format": "esm",
    "external": ["zod"],
    "minifySyntax": true,
    "minifyWhitespace": false
  }
}
```

#### Private Packages (`resolve-s3`)

The `resolve-s3` field is an array of package names that the server should download from S3 instead of npm. The version for each package is read from `dependencies` or `devDependencies` — do not duplicate it.

**Versions must be exact** (e.g., `"0.0.8"`, not `"^0.0.8"`). The server uses the version to fetch `packages/{name}/{version}.tgz` from the configured S3 bucket.

**How it works**: Before running `bun install`, the server downloads each `resolve-s3` package tarball from S3 and extracts it into `node_modules/`. Bun then sees these packages already installed (matching name + version in the lockfile), skips them, and only fetches public packages from npm.

**Tarballs** must be standard npm tarballs (what `npm pack` or `yarn pack` produces) — a gzipped tar with a `package/` root directory. They live in S3 at:
```
packages/@flickfyi/core/0.0.8.tgz
packages/@flickfyi/photon/0.0.3.tgz
```

If a private package has transitive dependencies on other private packages, those must also be listed in `resolve-s3`. Transitive dependencies on public npm packages are handled by bun normally.

If `resolve-s3` is absent or empty, the server behaves as a pure `bun install` from npm.

#### esbuild Configuration

The `esbuild` field maps directly to esbuild options. Only these fields are supported:

| Field | Type | Default | Description |
|-------|------|---------|-------------|
| `bundle` | bool | `true` | Bundle imports into a single output |
| `external` | string[] | `[]` | Packages to leave as `require()` calls instead of bundling. Use `["*"]` to externalize all bare imports. Default `[]` bundles everything. |
| `format` | `"cjs"` \| `"esm"` \| `"iife"` | `"cjs"` | Output module format |
| `minify` | bool | — | Shorthand: sets all three minify flags at once |
| `minifyIdentifiers` | bool | `false` | Shorten variable names |
| `minifySyntax` | bool | `true` | Simplify syntax constructs |
| `minifyWhitespace` | bool | `true` | Remove unnecessary whitespace |
| `platform` | `"browser"` \| `"node"` \| `"neutral"` | `"browser"` | Target platform |
| `target` | string | `"es2022"` | JavaScript target (`es2020`, `es2021`, `es2022`, `es2023`, `esnext`) |

**JSX settings** (factory, fragment, import source) come from `tsconfig.json`, not from the esbuild field.

**Externals behavior**: By default, all dependencies are bundled into the output (the platform does not support `require`). Setting `"external": ["zod"]` causes zod imports to remain as `require("zod")` calls in the output. Setting `"external": ["*"]` externalizes all bare imports.

### bun.lock

The `bun.lock` file is a lockfile generated by `bun install`. It pins the exact versions of all transitive dependencies. It serves as the **cache key** for the dependency cache: the server SHA256-hashes the raw lockfile contents to determine whether deps are already installed.

**Workflow**: Generate the lockfile at dev time in your repo by running `bun install`. Bundle the resulting `bun.lock` alongside `package.json` into your deployment. The server never resolves versions — it trusts the lockfile completely and installs with `--frozen-lockfile`.

**Private package requirement**: The lockfile must include entries for any packages listed in `resolve-s3`. This means the dev-time environment where the lockfile is generated must have access to the private packages — either pre-installed in `node_modules` or available via a local/private registry. When the server pre-seeds these packages from S3 before running `bun install`, bun matches them against the lockfile entries and skips re-downloading them.

If the lockfile doesn't include entries for private packages, `bun install --frozen-lockfile` will fail because it can't resolve them from npm and the lockfile has no record of them.

### tsconfig.json

If `/tsconfig.json` is included in the upload, the server parses its `compilerOptions` and uses them for the TypeScript-Go compiler. Supported fields:

| Field | Values |
|-------|--------|
| `strict` | `true` / `false` |
| `target` | `"es2020"`, `"es2021"`, `"es2022"`, `"es2023"`, `"esnext"` |
| `module` | `"commonjs"`, `"esnext"`, `"nodenext"` |
| `moduleResolution` | `"bundler"`, `"nodenext"`, `"node"` |
| `jsx` | `"react"`, `"react-jsx"`, `"react-jsxdev"`, `"preserve"` |
| `jsxImportSource` | any string (e.g., `"@crayonnow/core"`, `"react"`) |
| `lib` | string array (e.g., `["ES2022", "DOM"]`) |
| `skipLibCheck` | `true` / `false` |

If absent, the server uses these defaults (matching the v2 hardcoded options):

```json
{
  "compilerOptions": {
    "allowJs": true,
    "declaration": true,
    "esModuleInterop": true,
    "forceConsistentCasingInFileNames": true,
    "isolatedModules": true,
    "jsx": "react-jsx",
    "lib": ["ES2022"],
    "module": "commonjs",
    "moduleResolution": "bundler",
    "noEmit": true,
    "resolveJsonModule": true,
    "skipLibCheck": true,
    "strict": true,
    "strictNullChecks": true,
    "target": "ES2022"
  }
}
```

### Dependency Caching

Dependencies are cached in a 3-tier system to avoid repeated installs:

1. **Local disk** — `{DISK_CACHE_PATH}/deps/{sha256(bun.lock)}/node_modules/`. Checked first. Instant.
2. **S3** — `deps/{sha256(bun.lock)}.tar.gz` in the configured S3 bucket. Downloaded and extracted on local miss.
3. **bun install** — Runs `bun install --frozen-lockfile --ignore-scripts` in a temp directory. Result is cached locally and uploaded to S3 for sharing across server instances.

If multiple concurrent requests share the same `bun.lock` hash and all miss cache, only one runs `bun install`. Others wait and receive the same result.

Cached deps are evicted LRU-style (by directory mtime) when disk is full, alongside v1/v2 versioned caches.

## Authentication

The server supports optional HTTP Message Signature authentication ([RFC 9421](https://www.rfc-editor.org/rfc/rfc9421)) using P-256 ECDSA.

### Configuration

Set the `TSGO_AUTH_PUBLIC_KEY` environment variable to a base58-encoded compressed P-256 public key. If unset, the server runs without authentication.

### Signed Components

Clients must sign these components:

| Request type | Required signed components |
|---|---|
| Bodyless (GET, DELETE, HEAD) | `@method`, `@path`, `@authority` |
| With body (POST, PUT, PATCH) | `@method`, `@path`, `@authority`, `content-digest` |

Signatures must use `ecdsa-p256-sha256` and include a `created` timestamp. Signatures older than 5 minutes are rejected.

### Protected Routes

`/` and `/health` are always unauthenticated. All other routes require a valid signature when auth is enabled.

## Architecture

- **Go module**: `github.com/microsoft/typescript-go/serverexample`
- **Dependencies**: Uses vendored TypeScript-Go internal packages
- **File system**: Custom in-memory VFS implementation
- **Compiler**: Full TypeScript type checking and emission

## Files

- `auth.go` — HTTP message signature authentication middleware
- `Dockerfile` — Multi-stage build for static PIE binary (includes bun for v3)
- `go.mod` — Go module definition with TypeScript-Go dependency
- `Kraftfile` — Unikraft Cloud deployment configuration
- `resolver.go` — Node module resolution (package.json exports, main, extensions)
- `server.go` — Main server: routes, diskFS, v1/v2 handlers, S3 sync, disk eviction
- `server_metrics.go` — Prometheus metrics registration and helpers
- `v3_compile.go` — V3 compile logic: esbuild options, virtual-fs plugin, externals handling
- `v3_deps.go` — V3 dependency caching: hash, local/S3 lookup, bun install, concurrency dedup
- `v3_handlers.go` — V3 HTTP handlers for `/v3/typecheck` and `/v3/compile`
- `v3_multipart.go` — V3 multipart parsing, package.json/esbuild config extraction
- `v3_typecheck.go` — V3 typecheck logic: tsconfig parsing, compiler options, diagnostics
- `vendor/` — Vendored dependencies for offline builds
